# v1.5.4 出口混雑の再現・限定修正

## 基準と原因

基準はv1.5.3/main `289bf2e66673ba3f0bc15ae2311b704a0a1e0fac`。GitHub連携で取得したコードとGitオブジェクトをSHAで照合した。環境の通常のGitHub通信とnpm通信は制限されている。

convoy-escort・標準ON・seed15241・赤hard/青easyで、既存記録と同じT61青勝利を再現した。r1は(11,7)・HP100・燃料63・搭載なしで残る。T14にその位置へ到達し、その後は出口へ近づくマスを自軍に塞がれ待機を繰り返す。

既存の`evacuationAction`には撤退対象の閉塞を解く分岐があるが、護衛対象はその対象外。護衛は通常の行動順で進み、対象が判断する前に周辺の味方が行動を使い切る。既存の`clearCaptureLane`を撤退・占領へ一律適用し直す変更は行わない。

## 最終候補

`src/ai/missionLane.ts`で、護衛対象の地上補給車が実際の移動範囲で出口へ近づけない場合に限って経路を調べる。移動できる味方の占有を仮に外したグラフでも、地形・燃料・可視敵・ZOCを維持し、同じ手番で出口へ届く経路に限定する。実行は元stateで到達可能な退避先への一手だけ。次の判断で再計画する。

経路と出口へ戻る退避、施設・保持目標からの移動、別の任務対象・移動済み・行動済み・搭載部隊を持つ輸送役の流用を避ける。退避の安全性は既存のmissionSafetyと同じ公開装備・観測済み敵の移動/攻撃評価を使う。敵の私的資源は正規化し、非可視の接触は仮想移動で発見しない。

試作では撤退の順序変更と、経路が空いている護衛の前進への介入が別条件を悪化させたため、不採用とした。最終案は撤退に介入せず、前進できる場合も従来判断に任せる。これは全混雑・全任務の解決ではない。

## 実行済みの対局比較

Node 24.19.0のTypeScript型除去と[拡張子解決loader](v1.5.4/native-typescript-loader.mjs)で、既存のゲーム/CPUコードを直接実行した。npm依存導入失敗を回避して対局を確認したもので、Vitest・型検査・配布UI検証の代替とはしない。

- 既知seed15241・赤hard/青easy: T61敗北 → **T23達成**。命令と結果は[再現記録](v1.5.4/reproduction.json)。
- 26作戦×OFF/標準ON、赤hard/青easyの52条件: 達成46→46。51条件の全命令が一致。護衛ONの原典seedだけ命令が変わり、どちらもT7達成。
- 開発条件15411/15412、4任務×4難易度の32条件: 達成25→26。これらは候補調整に使った条件で、未使用条件とは扱わない。
- 最終候補固定後の未使用15421/15422、同じ32条件: 達成28→29。28条件の全命令が一致。変更前の勝利を敗北へ変えた条件はない。ただしseed15422・護衛・赤hard/青easyは、変更前のT61敗北に対して変更後もT16敗北となった。残る失敗を隠さず継続課題とする。未使用結果を見た後のCPU調整はない。

[比較一覧](v1.5.4/comparison.json)と各before/afterのJSONL・gzip命令履歴を保持する。`scripts/cpu-exit-v154.ts`は開発比較、[固定した未使用条件harness](v1.5.4/fresh-harness.ts.txt)はscripts直下へコピーして実行する。各JSONLの先頭に全game/AIソースとharnessのSHA-256、制限と実行環境を記録した。実行例:

```sh
node --no-warnings --loader ./docs/reviews/v1.5.4/native-typescript-loader.mjs scripts/cpu-exit-v154.ts after catalog output/catalog.jsonl
```
