# v1.4.3 操作応答・長期戦メモリ

## 基準と手順

公開済みv1.4.2のmain `9d056acaee825824d36e50a963102385e3fe7dd2`、tree `762c91c7c52a2c133ad3d8ec8277dd053fef0603`を基準とする。[計画](../plans/v1.4.3.md)だけのcommit `f47ab3e07320fc9373364a644cf24de73c325570`で[ドラフトPR #260](https://github.com/kumakumapon/MiniStr/pull/260)を作成後に製品コードへ着手した。

## 変更の対象

同期プロフィールでは、選択ごとに約3回のlayoutが発生し、スクロール復元の匿名関数が主要な処理時間を占めた。原点のスクロール領域へ0を書き戻す処理と、書き戻し後のページ位置の再取得を減らす。翻訳・inertの書き込みを復元前へ移し、更新途中での再配置を避ける。非原点のページ／盤面／生産メニューの位置、フォーカスの世代確認は維持する。

390幅のChromeタッチ回帰で、pointerupから遅れて来る互換focus／clickの前に情報欄が拡大し、最初のタップを取りこぼすケースを検出した。pointerupの0msタイマーで保護を解除せず、click確定までbriefを維持する。盤面外での終了・取消・次のポインター／キー操作では解除する。遅い互換イベント順の配布UI回帰と、3ブラウザの単発tap・スクロール保持回帰を追加する。

CPU Workerのonmessage／onerrorは完了・失敗・postMessage例外・取消時に解除する。稼働中のWorker再利用と遅い応答の拒否は維持し、処理済みinput.stateを閉包が保持する期間を短くする。

リプレイRuntimeは1個の所有snapshotを作り、timelineと表示が共有する。以前はtimelineが元のfile、表示が複製fileを保持し、全指令が二重に残っていた。現在位置とcheckpointの状態は独立させ、インポート元の変更や前後シークで記録を書き換えない。通常戦の指令・取り消し・保存内容を削らない。既存の規則版・各schema・CPU判断・マップ・依存は変更しない。

## 再実行

基準と改善後を別worktreeでbuildし、異なるlocalhost portのpreviewへ接続する。次のスクリプト自体は同じ版を両方に使う。重いテスト・build・別の性能計測と同時に実行しない。

応答は英語UI、fresh context、PC1280／390×844、16／32盤面、各条件2context×25回の合法な自軍ユニット選択。初回と残り24回、同期focus＋click handlerと2回RAFまでを分け、操作成立をassertする。実タッチ／キー操作とスクロール保持は別のブラウザ回帰で確認する。cold titleはlocalhostの新contextによる読込であり、実回線の初回表示を保証しない。DOMクリック時間を物理タッチ遅延とは扱わない。

メモリは390幅・wide-frontの実時間CPU観戦10分以上、6回のタイトル復帰、1,360手の完了済み32盤面リプレイ4回の読込・前後シーク・終了を測る。30秒ごとのmain／Worker heap、DOM／listener、120秒ごとのGC後、停止／終了後のWorkerを記録する。GC前の変動とGC後の保持量は区別する。GC・CDP自身の介入があり、1回の有限セッションから全環境の無漏洩を保証しない。指令履歴や再開に必要な状態の増加は不具合と決めつけない。観戦を保存するのは測定終了後の1回だけとする。

### 計測側の保持を分離

Playwrightのnative `setInputFiles`を使った往復では、GC後もタイトルのDOMが1回あたり約5,500増えた。fresh contextのヒープスナップショットで、切り離された5個のinputはすべて `(GC roots) → (Global handles) → DevTools console → HTMLInputElement` から保持されていた。[参照経路](v1.4.3/devtools-retainers.txt)と[診断raw](v1.4.3/devtools-retention.json)を保存する。別CDP sessionでの`Runtime.discardConsoleEntries`では解放されなかった[試行](v1.4.3/devtools-console-clear-attempt.json)も保持する。この増加をアプリのリークとは扱わない。

独立した`browser-replay-memory.mjs`では、DOM handleをNode側へ返さず、ブラウザ内でFile／DataTransferを作り、製品のchange→parseReplay経路で6回のインポート・前後シーク・全体視点・終了を測る。OSのファイル選択時間の計測ではない。元のnative計測も捨てず、10分観戦／Workerの評価と、DevToolsによる往復時保持の資料として残す。

10分基準run開始後にharnessのNode標準URL／timer／consoleの明示importとPrettier整形を追加したため、前後のファイルhashは異なる。観戦・GC・Worker採取・native取込・待ち時間・指令fixtureの手順は変更していない。応答3組と独立replay比較は各々同一hashのharnessを両版で使う。探索2秒runと途中停止runは別rawとして残し、10分の完了結果に数えない。

### リプレイの保持

同一harnessの6往復が前後とも完了。終盤3回の読込中heap中央値は **6,917,728→6,690,312 bytes**（約0.23MB減）。終了後は **6,058,164→6,071,856 bytes**でほぼ同等、各回DOM **6,826**／listener **153**、Worker **0**に戻る。必要な記録を保持したまま読込中の二重保持を減らしたことと、終了後DOMが積み上がらないことを確認した。[基準raw](v1.4.3/before-replay-memory.json)／[改善後raw](v1.4.3/after-replay-memory.json)。

### 実時間10分観戦

前後とも完了し、実観戦時間は600.600秒／600.598秒。終了後の新規スロットには711／712手の合法な指令が保存された。既存の指令を捨てずに進行・保存でき、停止後とタイトル往復後のWorkerはすべて0。

| GC後の値（bytes） | 基準 | 改善後 |
| --- | ---: | ---: |
| 観戦開始main heap | 6,053,112 | 6,039,520 |
| 観戦終了main heap | 7,515,208 | 7,466,840 |
| 観戦終了Worker heap | 976,428 | 1,035,756 |
| 停止後main heap | 7,472,444 | 7,432,044 |
| タイトル6往復後main heap | 7,721,440 | 7,694,904 |

終了時の1手差・進行状態・GCタイミングもあるため、長期観戦全体で大幅にメモリを削減したという結論にはしない。warmupと保持すべき指令履歴の増加を含み、すべてのheap増加の原因を特定したわけでもない。タイトル往復中のDOM／listenerは各run内で一定（基準6,941／176、改善後6,931／176）。rawのnativeファイル取込後のDOM増加は前述のDevTools保持なので、アプリの終了後DOM評価には独立replay測定を使う。

### 検証途中の失敗と修正

- 初回CIは計測script2本の`URL`未宣言でlint失敗。Node標準importを明示し、検査を維持して修正。
- 新規touch回帰の初回はChromiumで初タップが選択されず失敗、既存9件は成功。pointerup後の互換focusまでbriefを保護する修正後、Chromiumの同じ検査が成功。配布UIにも遅いイベント順の回帰を追加した。
- 初回のローカルcoverageは1,502件の検査が成功したが、UI・ブラウザとの並列負荷下で旧Vitestの`onTaskUpdate`通信timeoutが1件あり終了code1。UIも57成功／2件timeout・通信error2件。成功扱いにしない。UIを単独1workerで再実行すると**60件全成功**（追加回帰を含む、105.1秒）。既存timeout・coverage閾値・retryは維持。
- 変更モジュールの単体10件、型・lint・整形・build・リンク検査を実施。最終headの正式CI／全ブラウザ・最終ローカル再実行の結果は[PR #260](https://github.com/kumakumapon/MiniStr/pull/260)とIssue #168／#213へ記録する。途中headの成功を最終headの完了とは扱わない。

ローカルは既設のVitest3.2.7／Vite6.4.3／TypeScript5.9.3／Playwright1.62.1での診断。正式lockfileのVitest5／Vite8／TypeScript6／Playwright1.64とnpm監査・既存coverageゲートは正式CIで確認する。実機は既存方針どおり低優先度・未確認。
