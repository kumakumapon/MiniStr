# CPU 難易度の再設計 2026-09-27

対象: Issue #119 案B。判定勝ちで全局が決着する v3（#120）で計測した。

## 結論

- **難易度の順序を回復した**: 3つの対戦すべてで、上位の難易度が組単位で明確に勝ち越した。
- **方式**: 判断ロジック（重み）は全難易度で共通にし、難易度の差は CPU が動員する部隊数の上限の倍率（`forceLimitScale`: hard 1.0 / normal 0.7 / easy 0.45、最低 4）だけで付ける。
- 重みの差で難易度を付ける従来の方式は、計測で逆転（easy が最強）と三すくみが確認されたので、廃止した。

## 計測方法

- 同じマップ・同じシードで陣営を入れ替えた2局を「組」として集計し、組ごとの 2勝0敗・1勝1敗・0勝2敗の数を数える。陣営の偏りは組の中で打ち消し合うので、2勝0敗の数の差が実力差を表す。
- **計測環境の確認**: 同じ設定どうし（normal 対 normal）の35組は、陣営を入れ替えても完全に同じ試合になった（組ごとに必ず1勝1敗）。この計測で、赤青の勝敗は赤10・青25 だった。陣営の偏りは設定によって変わる。
- 対象: 判定勝ちの対象マップ7種（skirmish / islands / canyon / siege / river / marsh / admiralty）、近代ルール（v3）、最大60ラウンド。シードは 7919 の倍数。
- 実行方法: `simulateMatch`（`src/ai/balance.ts`）を直接呼ぶ一時スクリプトで、組単位の集計を行った。対局の単位の結果は `npm run balance -- --maps <7マップ> --rules modern --seeds 5 --difficulty hard --blue easy`（と、陣営を入れ替えた実行）で再現できる。
- コミット: `36e751b` 時点の CPU ロジック。

### 同じ難易度どうしの全体計測（`npm run balance -- --rules modern --seeds 3`）

- 未決着は 0%（99局。判定勝ち 63、生存 28、スコア 8）。
- 判定勝ちの対象マップでの陣営の勝敗は、赤26・青37 だった（#120 の時点では赤39・青24）。陣営の偏りは設定によって変わり、63局では統計的な差とは言えない（約1.4σ）。
- 平均の最大部隊数は、easy 23.6、normal 32.2、hard 42.5 だった。倍率どおりの規模差になっている。

## 調査の経緯（採用しなかった案）

- **従来の方式（重みの差）**: 7マップ × 3シード × 陣営の入れ替えで、hard 14 対 easy 28、normal 18 対 easy 24 と逆転していた。重みを組み替えた案は、三すくみになった（hard が normal に 21-7、normal と easy は 15-13、easy が hard に 16-12）。
- **判断の改善**（hard に適用）:
  - 占領部隊は拠点だけを目標にする: 32 対 38 で、互角まで戻るだけだった。
  - 敵の次の手番の移動範囲を危険として考慮する: 効果を確認できなかった。
  - 攻撃の安全マージンの変更: 効果を確認できなかった。
- **資金のハンディキャップ**（収入の一定倍を手元に残す）: 効果が一貫しなかった。CPU は部隊数の上限に先に達するので、資金は制約になっていなかった。
- **計測上の誤り（記録）**: 調査の途中で、試行ごとに設定を差し替える一時スクリプトが、前の試行で追加したキーを消していなかった（`Object.assign` はキーを削除しない）。そのため「easy と同じ設定」の試行（31 対 39）と、いくつかの試行の結果が汚染されていた。最終案の比較と上の結果は、キーを削除してから設定し直しているので、この問題の影響を受けていない。

## 残る課題

- 難易度の差は「部隊の規模」だけで、判断の賢さには差がない。判断の改善は、効果のある手法が見つかった時点で hard に追加する。
- ターン制限のあるマップでは、難易度の差が勝敗に現れない（陣営で決まる）。
- 人間が相手のときの体感（特に、easy の CPU の積極性）は未検証。
