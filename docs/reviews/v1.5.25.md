# v1.5.25：複数軍CPU・配置・長期保存と後続仕様

## 原因と限定修正

従来の未決着6条件をCPU v6で再現し、v1.5.22記録の全命令・最終状態ハッシュと一致することを確認した。戦線では生産と消耗が継続しており、単なる停止ではない。負傷した占領部隊まで補充済みと数えること、主弾薬枯渇後の帰還不足、戦車中心の補充、間接砲の前進、占領施設の占有、3軍以上が残る終盤の分散目標が司令部攻略を妨げていた。

CPU v7だけで、健全な占領部隊の確保・複数手番の修理帰還・観測済み装甲への限定砲兵補充・射程位置への進出・歩兵へ施設を空ける移動・40R以降の司令部重視を行う。上限内の歩兵補充を許すが、既存のハード上限は超えない。輸送艦はエンジンで合法な移動後の上陸を評価し、工兵は既知の自軍占領経路が改善する橋だけを建設する。CPUへ非公開の敵情報を渡さない。

新規3軍の「緑の国境」「前哨基地強襲」だけ、明示した配置v3を使う。北側の中立工場(8,5)→(8,4)、中立都市(7,4)/(9,4)→(7,3)/(9,3)の変更で、座標は0始まり。司令部・部隊・資金・他軍の施設は変更しない。初期司令部を前進する試案は学習用比較で不採用とした。その他の新規盤面、APIの既定値と旧保存の配置v2は維持する。

## 比較方法と結果

学習用seed152501/152502と未使用の検証用152509/152510/152511を事前に分け、検証前に[候補と8ファイルのハッシュ](v1.5.25/protocol.json)を固定した。検証結果から再調整していない。短期判定は3軍21R、4軍20Rの既存規則を使う。CPU・配置の組合せの比較であり、それぞれの因果効果を単独で推定するものではない。

[旧未決着6条件](v1.5.25/legacy-cutoffs-v6.json)は400Rまで継続し、改善版は[6条件すべて決着](v1.5.25/legacy-cutoffs-v7.json)した。回転同値の4条件は326R・14,325命令、設定違いの2条件は379R・19,895命令。400R・65,536命令の検証枠は変更していない。4条件は独立した4盤面ではない。未知敵で占有された生産施設などの拒否と安全な代替待機は集計し、ゼロと偽っていない。

## 水域・固定チームの長期保存

[実CPU12条件](v1.5.25/long-ai.json)は制限なし対局を160R／8,192命令まで実行し、合計43,920命令・58保存点を確認した。水域3軍／4軍の全軍敵対と固定チーム、陸上・広域4軍固定チームを2seedで試した。8条件が自然決着し、水域3軍全軍敵対2条件は160R、広域固定チーム2条件は8,192命令で打切りとなった。短期判定を無制限対局の決着と混同しない。

各保存点で全合法履歴・担当履歴・目撃履歴を検証して再開し、原本と再開後の最大512命令（自然終局・試験上限までの場合は実数）について命令・状態・RNGを照合した。256／1,024／2,048／4,096／6,144命令の到達点、100R停止境界、最終点を対象とする。最大保存は179,668バイト。実際の再生クラスで終端→巻戻し→再シーク、取消とキャッシュ上限も確認した。sourceHashesはこの長期報告だけ `sha256(JSON.stringify(UTF-8ファイル本文))` であり、他報告の生バイトハッシュと区別する。

別の[保存負荷4条件](v1.5.25/long-soak.json)では合法な待機を300Rまで実行した。3軍2,852命令、4軍4,802命令、100R／200R停止・再開、CPU→人間→CPUの担当履歴、全再生を確認した。これは保存の負荷試験であり、CPU実力や決着の評価には使わない。保存容量の上限65,536命令／8MB自体の負荷検証は従来の厳格なゲートを維持する。

## 互換性・後続仕様

CPU v1〜v6と配置v1／v2の判断を固定し、旧保存へ新CPUや配置を自動適用しない。外側schema6・engine5・match2のままCPU v7と、対象を限定した配置v3を検証する。CPU切替は今後の判断だけを変更し、マップ・状態・過去命令・原本を保持する。旧版は新CPU／配置の保存を明示的に拒否する。[旧CPU21条件・各最大512命令の一致](v1.5.25/legacy-compatibility.json)も公式v1.5.24実装と比較した。[通常2軍の本体77ファイル](v1.5.25/two-army-unchanged.json)はv1.5.24と同じGit blobである。

ユーザー指定により、途中参加・潜水艦・動的同盟は[仕様確定・保存互換・受入条件](../multifaction-v3-design.md)まで。予約参加・退出境界、2軍と共通の潜航／探知、全チーム同意と勝者固定、イベント検証を確定する。将来用の版番号は予約だけで、現行読込経路へ登録しない。将来schema・参入・外交・潜航入力を無書込みで拒否する回帰を追加した。

## 検証と公開判定

CPU回帰10件と保存互換4件を追加し、既存CPU31件・拡張盤面23件もローカルで成功。PC1280px／スマホ390px・日英の新3軍配置で占領・保存・読込・1手再生、旧CPU保持と明示切替の3 E2Eを実行し、`systems-v1525-three-*` の画像を確認した。同じケースをChromium／Firefox／WebKitへ追加する。物理端末で20〜30分の試遊を済ませたという意味ではない。

ローカルはNode24.19・TS5.9.3・Vite7.3.6・Vitest3.2.7・Playwright1.63／system Chromiumによる補助検証。JSDOMと固定依存の取得が制限されるため、全単体・厳格カバレッジ・配布UI・全ブラウザー・Node22.13・通常ビルド・監査はPRとmainの固定依存CIを公開条件とする。正式件数・run・Pages成果物と公開JavaScriptのSHAはReleaseに記録する。CI設定・閾値・監査例外・タイムアウト・Worker数・Pages条件は緩和しない。

初回PR CIでは、新規広域保存を旧schema4と決め打ちした既存E2Eの期待値漏れと、WebKitで短い演出が画像取得・操作の前に自動終了する競合を検出した。新CPUの保存はschema6と明示検証し、演出を確認するケースは既存の占領演出検証と同じ仮想時計で自動終了との競合を除いた。自動終了時間自体は既存の単体・統合テストで検証し、検査の対象数・時間上限・Worker数は維持する。

## 次の推奨順

1. 3軍戦術ONの北側の偏りと短期判定の引分1条件を診断。新seedを確保してから調整し、今回の検証用seedへの当て込みを避ける。
2. 水域3軍全軍敵対の未決着2条件、広域固定チームの8,192命令打切り2条件を診断。上陸・占領役・味方の動線・弾薬回復を優先する。
3. 物理PC／スマホで人間1軍＋敵CPUの20〜30分試遊を実施し、時間・操作負荷・納得感を確認する。
4. 確定した仕様に従い、予約参加、潜水艦、動的同盟を独立して実装・検証する。
