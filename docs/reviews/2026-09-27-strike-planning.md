# CPU の攻撃計画（制圧による決着と、判断の質による難易度差）2026-09-27

対象: Issue #122（#119 の残課題）

## 結論

- **原因**: CPU は「移動してから攻撃する」計画を持っていなかった。
  - 攻撃（`attackAction`）は、ユニットが今いる位置から届く敵にしか行わなかった。
  - 移動先（`moveAction` / `evaluateCpuPosition`）は、地形・目標までの距離・見えている敵からの危険で決めていた。「そこからどの敵を、どれだけの反撃で攻撃できるか」は評価していなかった。
  - このため攻撃は、移動の結果として敵の隣に止まったときに偶然起きるだけで、制圧に必要な戦力の削り合いが起きなかった。
- **対応**: 攻撃の段階の直後に、攻撃のための移動を選ぶ段階（`strikeAction`）を追加した。
  - 見えている敵と、霧を考慮した移動範囲（`reachablePositionsForPlayer`）だけを使う。
  - 移動先と目標の組を、与える損害（コスト換算）、受ける反撃、撃破、占領の阻止、移動先の地形で採点する。
  - 移動の後の手順で、既存の `attackAction` がその位置から攻撃する。新しい命令の種類は追加していないので、セーブ・リプレイ・画面の処理は変わらない。
- **難易度**: `CpuDifficultyConfig.strikePlanning` で割り当てた。
  - easy は 'none'（従来どおり）。
  - normal は 'lethal'（撃破できる攻撃と、占領の阻止だけ）。
  - hard は 'full'（有利な交換すべて）。
  - 部隊数の上限の倍率（`forceLimitScale`）は変えていない。
- **結果**: 同じ難易度どうしの対戦で、制圧による決着が 0 → 24局（264局中）になった。難易度の順序は3つの対戦すべてで、従来より大きな差で保たれた。部隊数を揃えた比較でも、攻撃計画を持つ側が勝ち越した。hard（'full'）の差は明確で、部隊の規模ではなく判断の差である。normal（'lethal'）も勝ち越したが、この標本数では統計的な差とは言えない（下記）。

## 計測方法

- 対局の計測: `npm run balance -- --rules modern --seeds 8 --rounds 60`（同じ難易度どうし、11マップ × 3難易度 × 8シード = 264局）。
- 組単位の計測: 同じマップ・同じシードで陣営を入れ替えた2局を「組」とし、2勝0敗・1勝1敗・0勝2敗の数を数える（`2026-09-27-difficulty.md` と同じ方法）。対象は判定勝ちの対象7マップ（skirmish / islands / canyon / siege / river / marsh / admiralty）、近代ルール、最大60ラウンド、シードは 7919 の倍数。`simulateMatch`（`src/ai/balance.ts`）を直接呼ぶ一時スクリプトで集計した。このスクリプトで従来のコードの hard 対 easy（5シード）を計測し直したところ、`2026-09-27-difficulty.md` の値（51 対 19、18 / 15 / 2）と一致した。
- 部隊数を揃えた比較: 一時スクリプトの中で、easy の設定を「hard（または normal）の設定のうち `strikePlanning` だけを 'none' にしたもの」に差し替えて、組単位で計測した。この差し替えはコミットしていない（`chooseCpuAction` は難易度の名前で設定を引くので、コミットするコードには片方の陣営だけ設定を変える手段がない）。
- コミット: 本文書を追加したコミットと同じ CPU ロジックで計測した（計測はコミット前の作業ツリーで行った）。

## 設計上の判断

- **本来の役割を持つユニットは、撃破できる攻撃だけに向かう**: 次のユニットは、撃破できる攻撃（または占領の阻止）のときだけ攻撃のために動く。
  - 占領ユニット。拠点の目標から外れないようにするため。
  - 補給ユニット（APC）。
  - 補給が必要なユニット。
  - 見えている敵の占領ユニットが届く位置で、自分の首都を守っているユニット。
- **自分の生産施設はふさがない**: その手番に使える自分の生産施設は、攻撃の位置の候補から除く。`evaluateCpuPosition` と同じ `blocksProduction` の判断を使う。
- **占領できる拠点には止まらない**: 占領ユニットは、敵または中立の拠点を攻撃の位置の候補から除く。次の手順で、攻撃より占領が先に選ばれるためである。
- **間接攻撃ユニットは対象外**: 移動した後は攻撃できないためである（従来の移動の段階が扱う）。
- **遭遇で止まった場合**: 見えない敵に遭遇して移動が止まると、そのユニットは移動済みになる。止まった位置から攻撃できる場合だけ攻撃し、計画し直しはしない。人間の移動と同じ処理なので、見えない敵の情報は漏れない。
- **採用しなかった案**（#122 のコメントに計測を記録）:
  - 敵の移動後の攻撃範囲を危険として数える。
  - 危険の重みを変える。
  - 判定を下すタイミングを変える。

  いずれも、片方の陣営だけに適用すると、その陣営が弱くなるか、変化がなかった。

## 性能

- 最終のコードで計測した結果: hard どうし、全マップ × 3シード、`chooseCpuAction` の呼び出し 32,452回で、1回あたりの最悪 6.2 ms（skirmish の1ターン目。実行開始直後の最適化前の値とみられる）、平均 0.50 ms（Node、一時スクリプト）。計画レビューでの試作の計測（最悪 6.3 ms、平均 0.69 ms）と同じ水準である。
- 単体テストに、全ユニットが攻撃の候補を持つ20ユニットの手番のベンチマークを追加した（既存と同じ 1秒の上限）。
- ブラウザでの処理時間は計測していない。

## 残る課題

- 人間が相手のときの体感は未検証。既定の難易度は normal なので、人間の対戦相手は従来より強くなる（撃破できる攻撃に向かうようになる）。
- ターン制限・生存・スコアで決まるマップ（landing / outpost / industrial / tundra）では、難易度の差は引き続き小さい。
- ZOC（#116 10.6）は、この変更の後に再評価できる。
