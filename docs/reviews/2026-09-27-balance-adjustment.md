# バランス調整の検討 2026-09-27

対象: Issue #116 Phase 10.4（新ユニットの価格・性能、修理費率、海峡総力戦の配置、陣営の偏り）

## 結論

- **ゲームの数値とルールは変更しない**: 計測の結果、調整の根拠になる偏りが見つからなかった項目と、CPU 同士の対戦特有の現象で人間のプレイに当てはまらない項目に分かれた（下記）。
- **不具合を1件修正した**: シナリオを保存用のデータに書き出すとき、ターン制限から自動生成した敗北条件（青の `survive untilTurn: turnLimit+1`）を、そのまま書き出していた。カスタムシナリオを保存し直すたびに、この条件が 1 → 2 → 3 と重複して増えていた。条件の数が上限（32）を超えると、保存したカスタムシナリオがすべて読み込めなくなるおそれがあった。組み込みシナリオの書き出しでも重複していた。
- ターン制限の意味を変える案（制限時点の判定勝ちにする）は、キャンペーンの landing・outpost の難しさが大きく変わるため、ユーザーの判断で見送った（industrial はスコアで決着しているので、影響は小さい）。

## 計測条件

- main `1f1f9a1` 時点（#121 の後）の CPU とルール（v3）
- `npm run balance -- --rules modern --seeds 8 --rounds 60`（同じ難易度どうし、各マップ24局、所要55秒）

## 陣営の偏り（各マップ24局）

| マップ | 赤勝 | 青勝 | 決着の仕方 |
| --- | ---: | ---: | --- |
| skirmish | 0 | 24 | 判定 |
| marsh | 3 | 21 | 判定 |
| islands | 6 | 18 | 判定 |
| admiralty | 6 | 18 | 判定 |
| river | 8 | 16 | 判定 |
| canyon | 10 | 14 | 判定 |
| siege | 18 | 6 | 判定 |
| landing | 0 | 24 | ターン制限（青の勝ち） |
| outpost | 0 | 24 | ターン制限（青の勝ち） |
| industrial | 2 | 22 | スコア（ターン制限は24局中1局） |
| tundra | 24 | 0 | 防衛戦（赤の生存。意図的に非対称） |

- #120 の時点（赤39・青24）とは逆に、#121 で判断の重みを共通にした後は、後手（青）が有利になっている。
- **判定の方式が主因とは考えにくい**:
  - 別の計測（判定勝ちの対象7マップ × 3シード × 3難易度 = 63局）で、ラウンド40の拠点数の優劣を、赤の手番の終了時と青の手番の終了時で比べた。入れ替わったのは63局中1局だけだった（赤優勢 17・青優勢 20・同数 26 → 17・21・25）。
  - 判定での部隊の価値から HP を除いても、判定勝ちの対象7マップの勝敗は 赤51・青117 → 赤55・青113 と、ほぼ変わらなかった。
- 推定される原因: CPU どうしの接近では、先に前進した赤が青の射程に入り、先制攻撃を受ける。**人間のプレイヤーは常に赤**なので、CPU 同士の陣営の偏りをルールで補正すると、人間の体感を歪めるおそれがある。そのため補正しない。CPU の改善は #122 で扱う。
- landing・outpost での青の全勝は、「ターン制限＝青の生存条件」という既存のシナリオ設計による。CPU が期限内に攻め切れないので、青が勝つ。人間（赤）にとっては「期限内に攻略せよ」という仕掛けであり、設計どおりとして維持する。
- industrial での青の優位（22勝）は、ほぼすべてスコア（12点）の先取による。ターン制限の設計では説明できないので、判定勝ちのマップと同じく、CPU 同士の後手有利の一部として #122 で扱う。

## 新ユニット

- 10.1 のベースライン（v2、旧来の重み）で見つかった「islands で重戦車に資金が偏る」（重戦車が約40両、修理費が約6.8万G）は、現行の CPU では再現しなかった。
- 各マップの生産上位は、歩兵・対戦車歩兵・戦車・砲兵・航空機で、新ユニットへの極端な偏りは無かった。例:
  - islands（hard）: 爆撃機 57、対戦車歩兵 35、歩兵 33、輸送艦 25
  - admiralty（hard）: 歩兵 168、戦車 119、砲兵 115、対戦車歩兵 28
- 数値を調整する根拠が無いので、変更しない。

## 修理費率

- 1局あたりの平均修理費（両陣営の合計、G）: admiralty 36211、siege 29740、islands 29443、skirmish 29088、river 23819、canyon 14864、tundra 10531、outpost 8541、industrial 1251、landing と marsh は 0。
- 修理費は、長期戦で前線が固定されるマップほど大きい。一方、どのマップでも判定まで部隊が枯渇することは無く（未決着 0%）、修理費が戦線を支えられないほど重いという兆候は無い。変更しない。

## 海峡総力戦（admiralty）

- 勝敗: 赤6・青18。easy・normal では青が 88%、hard では 50%。全局が判定で決着した。
- 偏りの向きは、ほかの判定勝ちの対象マップと同じ（後手有利）。admiralty の配置に特有の問題とは判断できない。
- #115 のリスク欄にあった「中央の港湾が詰まる」懸念は、判定勝ち（#120）で決着が付くようになり、実害は小さくなった。配置は変更しない。

## 修正した不具合

- 修正箇所: `src/game/maps.ts` の `scenarioDefinitionToData`。書き出すとき、`survive untilTurn === turnLimit + 1` の敗北条件をすべて取り除く（読み込み時の正規化で1件だけ再び追加される）。
- 既に重複して保存されたデータも、次に保存したときに1件に戻る。
- 自動生成の条件だけが敗北条件だった場合は、空のリストにならないよう1件を残す（読み込み後は同じ条件が2件になり、それ以上は増えない。勝敗への影響は無い）。
- セーブとリプレイにはシナリオの定義が含まれないので、互換性への影響は無い。
- 回帰テスト: `src/game/scenario-export.test.ts`（修正前は5件すべて失敗、修正後は成功）。
