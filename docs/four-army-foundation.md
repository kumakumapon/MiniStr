# 最大4陣営：初版の確定仕様と基盤（v1.5.9）

決定日：2026-11-12（Asia/Tokyo）。#275旧4のうち、初版範囲・脱落規則・ラウンド処理・保存互換の仕様を確定する。

v1.5.9は仕様と独立した参照モデルの提供段階である。4軍の戦闘・CPU・マップ・画面・保存本体の接続は次段階とし、本版にプレイ可能な4軍モードは追加しない。既存2軍のPlayerId・GameState・命令処理を拡張済みとは扱わない。

## 1. 初版の公開範囲

| 項目 | 確定した範囲 |
| --- | --- |
| 参加 | 従来2軍はそのまま維持。新規4軍は全軍CPU観戦 |
| 関係 | 各軍は他の生存3軍すべてと敵対。同盟・共有視界・共同資金・共同補給なし |
| 内容 | 専用32×32マップ1本。各軍の能力・戦闘数値に陣営固有の加算なし |
| 操作 | 軍別難易度・方針・視点、全体表示、速度、一時停止・再開、終了、軍別の識別表示 |
| 保存 | 最初のプレイ可能な提供から名前付き手動保存・再開・リプレイ・JSON入出力を必須とする。観戦の自動保存で既存対局を上書きしない |
| 勝敗 | 司令部喪失または全部隊喪失で脱落。最後の生存軍が勝利。全軍同時脱落は引き分け |
| 長期化 | 定時の勝者判定・60ラウンド期限は採用しない。100ラウンドごとに観戦を自動一時停止し、再開可能にする。停止を引き分けや勝利として記録しない |
| 後続 | 3軍、人間参加、交代、2対2、4軍エディタ・自動生成、キャンペーン・日替わり・研究分岐への拡張 |

軍IDは `army1`〜`army4` とし、色・表示名・開始方向・強さを判断規則へ埋め込まない。参加軍の並び、固定手番順、開始域、司令部、初期資金・部隊はマップの不変snapshotへ記録する。軍ID順と実際の手番順は別に扱う。

試作は各軍16・合計64部隊を比較値に使う。これは性能と攻略を未測定のため公開上限の確定値ではない。既存2軍の上限を下げない。配置・部隊表・経済初期値・公開上限は専用マップとCPUの試作・比較で決める。

## 2. 脱落と同時終局

1. 戦闘・反撃・同時射撃・占領・燃料死等の命令処理を終え、死傷と輸送参照を解決した同じ盤面を判定対象とする。
2. 生存軍ごとに、元の自軍司令部を保持しているか、1部隊以上存在するかを調べる。輸送中部隊も部隊数へ含める。生産施設や資金が残っていても全部隊喪失で脱落する。
3. そのsnapshotから脱落軍を一括決定する。軍ID・手番順に1軍ずつ勝者を確定しない。
4. 脱落軍の盤上・輸送中部隊をすべて除去する。他軍へ兵力・物資・資金を移管せず、孤立cargo参照を残さない。脱落軍は復活せず、収入・生産・補給・手番の対象から外れる。
5. 陥落司令部の占領軍が生存していれば、その軍の所有を維持する。占領軍も同時脱落した場合は中立化する。その他の脱落軍所有施設は中立化する。結果分析用の元司令部IDは保持する。
6. 生存軍が2以上なら続行、1ならその軍の勝利、0なら引き分け。次の軍の収入・修理を先に適用して結果を変えない。

参照モデルは、部隊ID・軍ID・輸送参照・施設ID・元司令部4件を検証する。輸送は同軍・実在・自己参照なし・入れ子なし。不正参照を黙って修復せず拒否する。入力は総128部隊/1024施設までに制限するが、これは計算境界で公開部隊上限ではない。戦闘後にHP0の部隊を残さない処理など、戦闘エンジンの接続は別途必要。

## 3. 手番とラウンド

固定手番順4件とカーソルで進行する。生存軍の先頭をラウンド基準にしない。ラウンド内で脱落軍の枠を飛ばしても、末尾から先頭への境界を越えたときだけラウンド番号を1増やす。先頭軍・末尾軍・現在行動中の軍が脱落しても同じ方式を使う。

保存する進行情報は次のとおり。

| フィールド | 意味 |
| --- | --- |
| `round` | 1始まりのラウンド番号 |
| `order` | 4軍を各1回含む固定手番順 |
| `index` | 現在の枠（0〜3） |
| `phase` | `pending`（開始処理前）／`active`（開始処理済み） |
| `startedArmies` | 初回の開始処理を既に受けた軍の集合 |

開始済みの手番を再開するときは、収入・補給等を再適用しない。`active`手番の再度の開始要求は副作用なし、開始前の終了要求は不正として拒否する。現在軍の脱落時は、その手番を1回だけ閉じて次へ進む。生存軍が1以下なら終局処理を優先し、次の手番を開始しない。

### 処理順

- 初期状態は全軍の基本資金を記録し、特定の先頭軍だけ開幕収入を先取りさせない。
- 各軍の手番開始は、行動状態更新→収入→自軍の期限切れ処理→維持燃料消費→施設/補給車等の補給→有償修理→燃料死→脱落/終局判定、の順とする。補給・輸送・修理・留保資金は自軍内に限る。
- 全軍とも自分の初回手番では維持燃料を消費しない。移動・戦闘の燃料消費は免除しない。次の自軍手番から維持燃料を消費する。
- 偵察・待伏せ・潜航等の期限は、その軍の開始/終了に対応させる。他軍の手番数が増えたことだけで、自軍の持続時間を短縮・延長しない。既存の一時偵察中心はその軍の手番終了時に失効させる。
- 手番終了は、その軍の目標進捗処理→脱落/終局判定→カーソル進行。ラウンド境界では、全軍のラウンド加点・天候更新・観戦停止判定を各1回だけ処理し、次の軍の開始処理へ渡す。初版では加点を定時勝利へ変換しない。
- 開始時の燃料死で現在軍が脱落した場合も、その枠を閉じて次の生存軍へ進む。境界イベントを二重発生させない。

v1.5.9の手番モデルは、二重開始防止・初回燃料フラグ・次の生存軍・完了ラウンドを返す。収入や天候そのものを変更する実エンジンではなく、次段階の処理順を検証する参照モデルである。

## 4. 保存互換の契約

- 従来2軍の保存/リプレイschema4、既知の旧schema、数値ruleVersionと乱数再現経路を維持する。旧ファイルや通常保存を4軍へ自動変換しない。
- 4軍は独立した外側コンテナ `ministr-four-army-save`／`ministr-four-army-replay`、それぞれschema1、`ruleset: four-army-v1`を識別子として予約する。
- 外側は `format`・`schemaVersion`・`ruleset`・`payload`。通常保存として成立するmapId・initialState等を外側へ並べない。通常schema4へ4軍フラグだけを付加する方式は使わない。旧アプリの通常保存・リプレイ・研究・復旧の読込で拒否できる境界を保つ。
- 4軍のpayloadは、マップsnapshot、正規初期状態、命令と行為軍、現在/最終状態、上記の手番情報、軍別CPU設定、乱数、視界・兵站・搭載・脱落履歴を再現する。全体観戦の表示設定はCPUへ渡さない。
- 本体の4軍GameState・命令schema・保存/再生器は次段階。v1.5.9には4軍ファイルのwriter/import routeや通常読込へのfallbackを追加しない。予約ヘッダだけで正しい4軍セーブと認定しない。
- 将来の保存先は `ministr.fourArmy.` 名前空間へ分離する。最初の4軍観戦は名前付き手動保存と書出しを提供し、通常自動/手動・既存観戦・研究・campaign・日替わりデータを上書きしない。
- 未知版・不正値・容量超過は明示的に拒否して原本を保持する。復旧で4軍データを通常2軍のスロットへ変換しない。
- 4軍を全データバックアップへ追加する際は、すべての内容を検証してから復元する。4軍キー入りバックアップを非対応旧版が拒否することを確認する。v1.5.9では新しい保存キーを書かない。
- 既存2軍の研究schema1と結果除外を維持する。初版4軍リプレイからの研究分岐、通常作戦記録・日替わり成績・キャンペーン進行への結果反映は対象外。

## 5. 次段階と公開判定

1. この参照モデルを実際の4軍状態・合法命令・戦闘/補給・視界へ接続し、小盤面で脱落・ラウンド・保存再開を通す。
2. 複数敵CPU・Worker取消、専用32盤面、軍別HUD/視点/難易度/方針/BGMを実装する。停止後の古いWorker応答で次手番を進めない。
3. 名前付き保存・JSON・決定的リプレイ・上限/未知版の保全・バックアップを接続する。これらを後回しにしてプレイ可能な初版を公開しない。
4. 手番の循環・逆順・隣接/対角が変わる入替、配置回転、seed/方針/難易度、総部隊数を揃えた2軍/4軍で、勝敗・脱落/決着ラウンド・到達・CPU時間・入力応答・メモリを比較する。90度対称だけで公平と判定しない。
5. 従来2軍の保存/再開・リプレイ・命令列/勝敗・観戦・研究・作戦記録を退行確認し、既存CI/Pagesの公開条件を保持する。

現行の「最大4陣営」残件は、仕様基盤の完了後も実対局提供まで継続する。仕様基盤と未提供のCPU観戦を同じ完了として計上しない。
