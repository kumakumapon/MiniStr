# v1.4.8 計画

基準は正式v1.4.7 main `f2746441154e648a951ea146d9edd8a492fb3854`、tree `e621b35e09acb047a1e532dfdff90c639ce961a3`。ローカルは同じtreeの `8ca38e857acb7ebf5e536dc29eabda907825bc69` を凍結する。Issue #264で承認された「CPUの回復と目標保持＋初回選択・復帰の応答改善」を実装し、v1.4.8へ同期する。

## 順序と完了条件

1. 計画だけでドラフトPRを作成してから製品コードへ着手する。
2. CPU：既知32内陸・沿岸の判断差3例を再現し、回復・目標保持・守備交代の競合を確認する。合法な対局や小さなfixtureで検討し、実証した問題に対する変更を実装する。単に低HP部隊を危険な拠点へ固定する調整は採用しない。公開情報・自軍資源・期限・代替守備・修理距離／前線復帰など、既存規則の範囲で必要な判断を選ぶ。
3. CPU変更は既知条件と未使用seed、先後・方針・難易度・目標を固定して比較する。勝敗に加え目標保持・修理／補給・退却／復帰・対局長を記録し、改善／悪化を併記する。合法性・決定性・可視情報限定・不変state・実行予算と旧ルールを維持する。勝率や全マップの公平性を少数条件から断定しない。
4. 応答：初回選択・連続操作・タイトル表示と復帰を別々に計測する。390幅／32盤面に加えPC・16盤面の対照、倍率・密集部隊を確認する。まずprofileで生成・翻訳・再配置・入力の処理を分け、測定で確認した負荷を削減する。Chromium／Firefox／WebKitはそれぞれ同じharness・ツール・環境で変更前後を交互に比較し、エンジン起動をアプリから分離する。
5. フォーカス・スクロール・ズーム・最初のタップ・日英・観戦停止・リプレイを守る。関連する保存／入力境界、旧データ・マップ定義の不変性を回帰確認する。画面変更のないUI更新は必要な範囲で整理し、無関係な全面再設計をしない。
6. 回帰テスト・型・lint・整形・単体／coverage・build・配布UI・全3ブラウザー・リンク・CI条件・Node22.13・最新監査・CodeQLを確認する。既存のcoverage・アプリ30秒・地形33回／2workers／色差・retryなし・公開条件／権限を維持する。手元の旧ツール／不足するnative WebKit環境は正式CIで補い、失敗を成功として数えない。
7. 生データ・固定source／harness・再現手順・失敗履歴・限界を記録する。package／lock・README・公開ノートを1.4.8に同期し、Issue #264とPRを更新してReadyにする。マージ後のmain／Pagesを確認して正式Releaseを準備する。

新しい戦闘規則・マップ再配置・保存形式変更・軍方針／指揮官・PWA・キャンペーン拡張は今回追加しない。依存追加は必要な場合だけ。テストの追加・実行は既存の明示的承認に従う。
