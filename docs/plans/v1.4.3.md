# v1.4.3 計画

## 基準と対象

基準は公開済みv1.4.2のmain `9d056acaee825824d36e50a963102385e3fe7dd2`（tree `762c91c7c52a2c133ad3d8ec8277dd053fef0603`）。390幅の操作応答と、長期戦・画面往復・リプレイ・実行中Workerのメモリを計測して改善する。Issue #168／#213の次候補に対応する。

## 手順・完了条件

1. この計画だけでドラフトPRを作成してから製品コードへ着手する。
2. 基準ビルドを固定し、PC1280／390幅・16／32盤面で実際の部隊選択、初回表示、タイトル復帰等を計測する。操作の成立をassertし、初回と連続選択のp50／p95、同期handlerと描画を含む時間、long taskを分ける。同じharness・ブラウザ・条件で前後を交互に3組以上比較し、全raw・再実行方法・失敗と制限を保存する。重い計測・テストを同時実行しない。
3. CPU観戦の長時間稼働、繰り返す画面遷移、長いリプレイ、稼働中／停止後Workerを対象に、時間・指令数とheap／DOM／イベントリスナー／Worker保持量を記録する。GC前後を分け、必要な指令履歴の増加と不要な保持を区別する。10分以上の観戦を含む基準／改善後の同条件比較を行い、短い往復や一度のGCだけで長期改善を判定しない。
4. 計測結果に基づき描画・入力・キャッシュ・状態の寿命を改善し、追加の回帰で表示更新・フォーカス・タッチ／キーボード・CPU応答取消・観戦停止と保存保護を確認する。セーブ／リプレイの履歴を削らず、ゲーム規則・CPU判断・マップ・保存schema・依存を維持する。
5. 単体・配布UI・ブラウザ回帰、型・lint・整形・既存coverage・build・リンク検査を実行し、正式lockfile CI・Node22.13・CodeQL・全ブラウザ・地形反復を確認する。閾値・timeout・retry・公開条件・権限は緩和しない。ローカル既設依存の診断、正式CI、実機未確認を区別する。
6. package／lock・README・公開ノートを1.4.3へ同期。計測結果・採否・残件をPRとIssueへ記録し、最終CI成功後にレビュー可能へ変更する。
7. マージ後main CI／CodeQL・Pagesと対象SHAを確認してからv1.4.3を正式公開する。実機確認は既存方針どおり低優先度とし、ローカルの390幅エミュレーションを実機の改善保証には使わない。
